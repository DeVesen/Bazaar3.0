# app-input — eigenständige Text-Input-Komponente

## Was, wie, wo, warum
Neue, eigenständige Haupt-App-Komponente `app-input` für einzeilige Text-Eingabe, aufgebaut nach dem PrimeNG-`p-iftalabel`-Muster (Float-Label). Verwendet ausschließlich PrimeNG-Elemente direkt (`p-inputgroup`, `p-inputgroup-addon`, `p-iftalabel`, `pInputText`) — keine eigenen `app-...`-Unterkomponenten, unabhängig von `app-input-group`. *Aussage*

Geltungsbereich gedanklich suite-weit, umgesetzt aber ausschließlich in der Haupt-App (`src/bazaar-app/frontend`) — die Voranmelde-App wird nicht angefasst. *Aussage*

Wertetyp ausschließlich Text (`string`) — kein Zahlen- oder Passwort-Modus; dafür bleiben `p-inputnumber`/`app-input-group` bzw. `pInputPassword` zuständig. *Aussage*

Verhältnis zur bestehenden `app-input-group`: bewusst zwei getrennte Vorgänge. `app-input-group` (Multi-Modus Tastatur/Kamera/Numpad, Varianten search/price/count) bleibt unverändert bestehen. Eine spätere, gezielte Prüfung einzelner `app-input-group`-Einsatzstellen auf Ablösung ist ein eigener, späterer Auftrag. *Aussage*

Migration bestehender nackter `pInputText`-Stellen ist **nicht** Teil dieser Spec — die zuvor gelieferte Liste war nur Information, kein Akzeptanzkriterium. *Aussage*

## Theoretisches Verhalten nach Umsetzung
- Ist `label` gesetzt (nicht-leerer String), rendert die Komponente `<p-iftalabel><input pInputText .../><label>{{label}}</label></p-iftalabel>` — Float-Label-Verhalten wie im PrimeNG-Referenzbeispiel.
- Ist `label` nicht gesetzt, rendert die Komponente das nackte `<input pInputText .../>` ohne `p-iftalabel`-Wrapper.
- `addonLeft`/`addonRight` (je `InputAddon[]`) rendern, sofern nicht leer, je Eintrag ein eigenes `p-inputgroup-addon` links bzw. rechts vom Input/`p-iftalabel`, in Array-Reihenfolge. Leeres Array → kein Addon-Slot auf der jeweiligen Seite.
- Jeder Addon-Eintrag (`type: Label|Icon|Button`, `value`, `key`, `class`, `style`) ist unabhängig vom `type` klickbar; ein Klick emittiert `addonClick` mit dem Addon-`key`.
- `keyUp`, `keyDown`, `blur` reichen das native Browser-Event (`KeyboardEvent`/`FocusEvent`) unverändert 1:1 an das Parent durch — synchron, ohne Verzögerung.
- `enter` (Enter-Taste im Feld) feuert sofort, unabhängig vom Debounce.
- `valueChange` ist der gedämpfte Werte-Stream (entspricht dem ursprünglich genannten „OnChange"): bei jedem Tastendruck aktualisiert, aber erst nach Ablauf von `debounceMs` seit der letzten Änderung emittiert (Default 800ms, konfigurierbar über den Input-Parameter `debounceMs`).
- Der Wert selbst wird über einen `value`-Input-Parameter hereingereicht (kein Zweiwege-Binding, kein `ControlValueAccessor`) — Parent hält den Wert, `app-input` emittiert nur.
- Standard-HTML/PrimeNG-Attribute (`id`/`inputId`, `name`, `placeholder`, `required`, `disabled`, `readonly`, `type` als text/email/tel o.ä.) sind zusätzliche Parameter, unabhängig davon ob `label` gesetzt ist.
- Pflichtfeld-Stern (`*`) neben dem Label und Feldfehler-Text darunter (Doc `form` R-1) bleiben weiterhin Aufgabe des Parent-Templates, außerhalb von `app-input`.

## Soll-Vorgaben
- Keine eigene Business-Logik, kein API-Aufruf (Dumb Component, `docs/components/overview.md`).
- Ausschließlich PrimeNG-Elemente direkt verwendet, keine Komposition mit anderen `app-...`-Komponenten.
- Event-Namen ohne `on`-Präfix, konsistent zu bestehenden Komponenten: `valueChange`, `enter`, `keyUp`, `keyDown`, `addonClick`, `blur`.
- `debounceMs: number`, Default `800`; `0` bedeutet kein Debounce.
- Icon-Werte in `InputAddon.value` folgen der Projekt-Konvention `pi pi-...`-CSS-Klasse (nicht `data-p-icon`).

## Akzeptanzkriterien
- Gegeben `label` ist gesetzt, wenn die Komponente rendert, dann erscheint das Feld innerhalb von `p-iftalabel` mit Float-Label-Text.
- Gegeben `label` ist nicht gesetzt (undefined/leer), wenn die Komponente rendert, dann erscheint ein nacktes `pInputText`-Feld ohne `p-iftalabel`.
- Gegeben `addonLeft`/`addonRight` sind leer, wenn die Komponente rendert, dann erscheint auf der jeweiligen Seite kein `p-inputgroup-addon`.
- Gegeben ein Addon mit `key: "x"`, wenn darauf geklickt wird, dann emittiert `addonClick` den Wert `"x"` — unabhängig vom `type` des Addons.
- Gegeben der Nutzer tippt schnell hintereinander, wenn seit dem letzten Tastendruck `debounceMs` (Default 800ms) vergangen sind, dann emittiert `valueChange` genau einmal mit dem finalen Wert — nicht bei jedem Tastendruck.
- Gegeben `debounceMs="0"`, wenn getippt wird, dann emittiert `valueChange` sofort bei jedem Tastendruck, ohne Verzögerung.
- Gegeben der Nutzer drückt Enter im Feld, wenn das passiert, dann emittiert `enter` sofort, unabhängig vom laufenden Debounce-Timer.
- Gegeben `keyUp`/`keyDown`/`blur` treten auf, wenn sie gebunden sind, dann erhält das Parent jeweils das native Browser-Event als Payload.
